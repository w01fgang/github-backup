<staleness_math>
**D-10:** Parse `CRON_SCHEDULE` (5 fields: min hour dom mon dow) to compute the expected interval in seconds.

Acceptable simplification for v1: use a small bash function that recognizes the common patterns from `config.example.json` and the field defaults:

| CRON_SCHEDULE pattern         | Expected interval (seconds) |
|-------------------------------|-----------------------------|
| `*/N * * * *`                 | N * 60                      |
| `0 */N * * *`                 | N * 3600                    |
| `M H * * *`     (M, H literal)| 86400 (daily)               |
| `M H * * D`     (D = single day)| 604800 (weekly)           |
| `@hourly`                     | 3600                        |
| `@daily` / `@midnight`        | 86400                       |
| `@weekly`                     | 604800                      |

If the pattern does not match any of the above, default to `86400` (assume daily) and add a key `staleness.parser_warning: true` in JSON output.

Then: `THRESHOLD = 2 * INTERVAL`. Compute `AGE = now - finished_at`. If `AGE > THRESHOLD`, state is `STALE`. Otherwise `OK`.

This is intentionally not a full cron parser — D-CTX says "Whether to use cron-parser npm package vs hand-rolled" is Claude's discretion, and we're on droplet bash so npm packages are out. The lookup table covers the realistic schedules a single operator uses and degrades gracefully.
</staleness_math>

<disk_block>
**D-08:** Always emit two values:
- `df -P -B1 "${BACKUP_DIR}" | awk 'NR==2 {print $1, $2, $3, int($3*100/$2)}'` → filesystem, size_bytes, used_bytes, percent_used. `-P` forces POSIX output (single line per FS). `-B1` forces byte units (no Ki/Mi rounding ambiguity).
- `du -sb "${BACKUP_DIR}" | awk '{print $1}'` → mirror_bytes.

For text mode, format bytes as human-readable with awk:
```bash
human_bytes() {
  awk -v b="$1" 'BEGIN {
    split("B K M G T P", u);
    for (i=1; b>=1024 && i<6; i++) b/=1024;
    printf "%.0f%s", b, u[i]
  }'
}
```
</disk_block>

<exit_codes>
**D-13:**
- `0` — last run succeeded AND not stale
- `1` — last run had failures (`fail > 0` OR `exit_code != 0`)
- `2` — last run is stale (regardless of success/failure)
- `3` — never ran / state file unreadable AND log has no recognizable summary

Order of evaluation: `3 > 2 > 1 > 0`. If both stale AND failed: report `2` (stale dominates — fixing the freshness is the prerequisite).
</exit_codes>
