<schema>
**`/var/lib/github-backup/last-run.json` — locked schema** (Plans 02, 03, 04 read this exact shape; do NOT diverge):

```json
{
  "started_at": "2026-05-12T03:30:01Z",
  "finished_at": "2026-05-12T03:31:42Z",
  "exit_code": 0,
  "total": 13,
  "success": 12,
  "fail": 1,
  "repos": [
    { "name": "sumin/dotfiles", "action": "update", "duration_ms": 1240 },
    { "name": "sumin/new-repo", "action": "clone", "duration_ms": 5810 },
    { "name": "sumin/broken-repo", "action": "fail", "duration_ms": 320 }
  ]
}
```

Field rules:
- `started_at`, `finished_at`: ISO-8601 UTC, second precision, `date -u -Iseconds` or `date -u +%Y-%m-%dT%H:%M:%SZ`.
- `exit_code`: integer; `0` if `fail == 0`, else `1` (matches existing script's exit semantics at line 193-195 of github-backup.sh).
- `total`: integer count of repos enumerated from GitHub API for this run.
- `success`, `fail`: integer counters already maintained in the script (lines 145-146, 166, 169, 178, 181).
- `repos[].name`: `OWNER/REPO` (already `${REPO_FULL}` in script).
- `repos[].action`: enum string `clone | update | fail`. Per D-12, "skipped" does not exist in this script. `clone` = new mirror created; `update` = existing mirror refreshed; `fail` = either clone or update returned non-zero. Mapping below.
- `repos[].duration_ms`: integer milliseconds. Measure with `EPOCHREALTIME` (bash 5+, available on Ubuntu 22.04/24.04) or `date +%s%3N`. Per-repo timing OPTIONAL but RECOMMENDED — if measurement complicates the loop, omit the field entirely for that repo rather than emitting null/0.
- File ends with a single trailing newline.
</schema>

<atomic_write>
Standard idempotent pattern:
```bash
TMP="${STATE_DIR}/last-run.json.tmp"
jq -n --arg started "$STARTED_AT" --arg finished "$FINISHED_AT" \
  --argjson exit "$EXIT_CODE" --argjson total "$TOTAL" \
  --argjson ok "$SUCCESS" --argjson failed "$FAIL" \
  --argjson repos "$REPOS_JSON" \
  '{started_at:$started, finished_at:$finished, exit_code:$exit, total:$total, success:$ok, fail:$failed, repos:$repos}' \
  > "$TMP"
mv -f "$TMP" "${STATE_DIR}/last-run.json"
chmod 640 "${STATE_DIR}/last-run.json"
```
`mv` on the same filesystem is atomic on Linux. `jq` is already installed by bootstrap.sh (line 60-65).
</atomic_write>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| droplet root user → /var/lib/github-backup/last-run.json | Single-tenant droplet, root-owned state, mode 640. No untrusted input enters here. |
| github-backup.sh ↔ jq | jq receives only values from `gh api` (GitHub repo names) and internal counters. Values pass through `--arg`/`--argjson` flags which jq escapes correctly. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | last-run.json atomic write | mitigate | temp+rename on same filesystem prevents half-written reads (D-03) |
| T-02-02 | Information Disclosure | last-run.json file mode | mitigate | chmod 640, parent dir 700 — only root and the (unprivileged) reader the operator chooses can read; never world-readable |
| T-02-03 | Injection | repo names from gh api into jq | accept | jq `--arg`/`--argjson` handles escaping; GitHub repo names are alnum + `-_./` and would not break JSON even if passed unescaped |
| T-02-04 | Denial of Service | unbounded REPOS_JSON_ROWS array | accept | Bounded by GitHub API page limit (~100 repos/page, typical operator ≤ a few hundred repos); no realistic memory pressure on a $6 droplet |
</threat_model>
